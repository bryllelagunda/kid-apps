## Problem Statement

The `kid-apps` launcher has two tiles. Crane Stacker teaches letter and number recognition through block stacking. Printables makes paper worksheets for a parent to hand over. Neither is a *game you play against someone*.

Castle Blasters is the third app: an original, offline, turn-based physics artillery game where players slingshot projectiles at each other's block castles until one player is left standing. It must work as a solo toy on a Tuesday afternoon with a 4-year-old and one CPU opponent, and as a family game on a Sunday with three or four humans passing one tablet.

The source spec described a much larger game. This document is the cut-down that actually gets built.

## What Makes This Cool

**The tower falling over.** That's the whole product. Everything else is scaffolding around a 4-year-old watching a stack of blocks come apart because of something they did with one finger.

Three things sharpen it:

1. **The CPU is a clown, not a rival.** Difficulty is aim error, never damage multipliers. An easy bot overshoots wildly, and on a fixed percentage of shots it fires a deliberate "silly shot" that can land on its own castle. Angular error alone lands short or long *on the correct side* and essentially never behind the shooter, so the silly shot has to be an explicit mechanic rather than an emergent one. See `cpu`.
2. **Letters and numbers are already in the world.** Every castle block wears one permanently. Learning is not a mode you enter, it's the material the castle is made of. Sometimes a block on an opponent's castle starts glowing and a voice says "hit the seven."
3. **The printable battle poster.** When the match ends, freeze the canvas and offer print-or-save. The kid's demolished castle becomes paper on the fridge. Credit: Codex cold read. Scope is a raw canvas screenshot, not line-art conversion.

## Constraints

From the workspace `CLAUDE.md`, non-negotiable:

- **No build step.** No webpack, vite, rollup, bundler, transpiler, or framework.
- **No npm dependencies.** CDN only. Matter.js v0.19.0 from the identical jsdelivr URL `crane-stacker/service-worker.js:15` already caches.
- **No shared code between apps.** Patterns get copied, never imported (workspace rule 2).
- **No database, no auth, no accounts, no gameplay network calls.** `localStorage` only. (The app does fetch Matter.js and Google Fonts from CDN on first load, exactly as the two existing apps do; both are precached by the service worker for offline use.)
- **No ads, analytics, or third-party tracking.**
- **All paths relative.**
- **One subdirectory per app**, with its own `manifest.json`, `service-worker.js`, icons, `README.md`, `CLAUDE.md`.
- **Bump `CACHE_VERSION` on every deploy**, without exception. The Crane Stacker service worker pattern this design copies is cache-first and precaches `./index.html`, so shipping any change without a bump strands every installed client on the old build permanently.

From `DESIGN.md`:

- Display type Lilita One, body type Fredoka. Do not deviate.
- Launcher colour slot 2 is `#ffd700` golden yellow. This game claims it permanently.
- Ink `#2a1a0a`, cream `#fff8e7`. The accent set is resolved to roles in Architecture → Palette.
- `DESIGN.md` says nothing about device or orientation. That requirement comes from source spec §29.

Device target (from §29; restated because the P5 geometry argument depends on it):

- **Primary: tablet landscape.** Reference device for all sizing here is **1024 × 768 CSS px** (iPad 9.7"/10.2" landscape). Larger tablets get the same world, letterboxed.
- Desktop mouse must work. Portrait is a heavily letterboxed landscape world and is a **tested** case, not an aspiration.

Audience: primary player is a 4-year-old who does not read fluently; secondary players are family and friends of mixed ages; the parent is the only one who touches settings.

## Premises

All eight were agreed in session. **P5 was revised** in response to the Codex cold read; the revision was accepted in session.

**P1 — Ground is fixed, castles are destructible.**
Terrain is a static Matter.js body and is never deformed. Castles are stacks of discrete rigid blocks. **v1 ships two materials: wood (1 hit) and stone (2 hits).** Ice is cut (see Scope note below).

*Why:* destructible terrain and destructible structures are different engineering problems. Crater digging needs bitmap masks, marching squares, and polygon re-triangulation, and Matter.js has no boolean geometry. Knocking over a block tower is native rigid-body physics that Crane Stacker already does with the same library on the same device class. Worms needs crater digging because terrain deformation is its strategic core; a 4-year-old does not do terrain strategy.

*Ice was cut* because its only stated purpose was low friction, which mainly creates long roll-outs that the turn-end hard cap then has to absorb. It exists to create a problem. Two materials read as clearly different to a preschooler; three do not.

*On performance:* this document makes **no** claim about measured frame rate. Nothing in the repo records one; `crane-stacker/CLAUDE.md:108` in fact records a V3.1 stability fix under block load. A body budget and an M1 measurement gate are specified in Architecture → Performance budget.

**P2 — One gesture, not three.**
Touch down anywhere in the active player's slice of the world, drag, release. Direction and drag distance encode angle and power together in one continuous touch. A dotted arc previews the shot live while dragging. No power meter, no angle buttons, no wind.

*Also cut here, explicitly:* source spec **§11 (8 weapon types) and §12 (special abilities) are out of v1 entirely.** One projectile type, no weapon UI, no abilities.

**P3 — Every player slot is HUMAN or CPU.**
Set per slot at setup. The turn manager treats both identically. The pass-the-device screen appears **only when the next player is human**, so a solo game never shows one. CPU difficulty is aim error, never damage multipliers.

**P4 — Learning is ambient plus optional bonus targets.**
Castle blocks carry letters and numbers permanently. Sometimes a block on an **opponent's** castle glows with a spoken prompt ("hit the seven"). Hitting it awards points and confetti; missing it does nothing.

Explicitly **not** built: math questions, multiple choice, comparison prompts, quiz screens, educational difficulty tiers, badges, sticker economies, cosmetic unlocks. Source spec §14–17 is reduced to about a sixth of its scope. (The CPU *does* have three difficulty tiers — that is aim skill, not an educational tier, and it is unrelated to this cut.)

**P5 (REVISED) — One game mode, 2 to 4 players.**
Free-for-all, last player standing, points as the tiebreak. v1 offers 2, 3, or 4 slots, **at least one of which must be HUMAN**.

*Originally 2 to 8.* Revised after Codex challenged it and the arithmetic confirmed the challenge: 8 castles across 1024 CSS px gives each castle 128px, and a 3-block-wide castle at 40px per block is 120px — an 8px gap, with no room for the character or for labels to read. At 4 players each castle gets 256px and breathes.

**The path to 5–8 players is teams, not shrinking.** Two teams sharing two castles, alternating turns within the team. Deferred to v2. The only v1 concession is that `castleId` is a separate field from `id` on the player slot.

Also deferred, not cut: Castle Siege, Boss Battle, Learning Challenge (§22). The turn timer (§21) is deferred; the soft-lock role it would have played is covered explicitly by `TURN_MAX_MS`.

**P6 — Same stack, same rules as the rest of the repo.** New subdirectory `castle-blasters/`, single `index.html` with everything embedded, Matter.js v0.19.0 via the same jsdelivr URL, own PWA files. No build step.

**P7 — Distribution is already solved.** See Distribution Plan.

**P8 — Audio is synthesized, never downloaded.** Web Speech for letters and numbers, WebAudio for cues, zero audio files. The non-obvious parts to copy are in Architecture → Audio; they are not the parts that look important.

*Correction to existing repo docs:* `crane-stacker/CLAUDE.md` states sound effects are blocked because they "need hosted audio files." That is false — WebAudio synthesizes all four cues with zero assets. Correcting that line is a task in Next Steps.

## Cross-Model Perspective

Independent cold read from Codex (gpt-5.5, high reasoning, read-only against the repo), which had not seen the conversation.

**Coolest version it proposed — "Build it, blast it, print it."** A 30-second castle-builder phase where the kid drags blocks onto their base, then the CPU auto-builds, then battle, then a printable "battle poster" of the wreckage in colouring-page line art.

**What it said reveals the most,** quoting the session:

> "no i want all computer opponent for 1 player or vs playera. This is offline.."

Its read: *"They are not excited by multiplayer architecture. They are excited by a real tablet toy that works at home, in the car, with family, without accounts, servers, or setup friction."*

**Premise it attacked:** P5. Accepted and revised above.

**Where this document disagrees with Codex, and why:**

1. **Castle-builder phase: deferred.** A second full interaction mode (drag, snap, validate, prevent unstable configurations), substantially redundant with Crane Stacker, which is already a block-stacking game the kid owns. Deferring costs nothing because the castle is a plain data descriptor.
2. **Battle poster: accepted, raw canvas screenshot only.** Line-art conversion is an edge-detection or outline-re-render pass, not a small feature.
3. **Its Matter.js recommendation is wrong for this design.** Codex proposed following Matter's official `slingshot.js`. That example drags the *body* with a `MouseConstraint` against an elastic `Constraint`, so release velocity is emergent from a spring. This design derives angle and power from the drag vector and applies `Body.setVelocity` directly. The two are mutually exclusive, and the constraint version is exactly what makes an accurate preview impossible. **The slingshot is drawn, not simulated.**

## Approaches Considered

**A: Vertical slice, then grow.** Hardcoded 1v1, no setup screen, bolt on slots later. Effort S-M · Risk Low · Completeness 6/10. Rejected: the turn manager gets retrofitted around hardcoded two-player assumptions, the exact bug class §32 warns about.

**B: Full v1 in staged milestones — CHOSEN.**

**C: Sandbox toy first, game later.** No turns, no opponent, no score. Effort S · Risk Low · Completeness 3/10. Rejected: it isn't the ask, and the tile would promise a battle that isn't there.

## Recommended Approach

**Approach B, five staged milestones.**

The deciding factor: a wrong design gets built at full speed, so design correctness is the binding constraint. Staged milestones buy Approach A's early feel-validation without its turn-manager retrofit.

**Effort is deliberately not estimated in hours.** The only honest reference in the repo is `crane-stacker/index.html` at 1,035 lines for a single-mechanic game with no opponent, no turns, no shell. Plan for several sessions per milestone. The gates below, not a time budget, say whether it is on track.

**Resolve before M1:** Open Questions 1 and 2.

### M1 — Feel *(the entire bet)*
Canvas, fixed world, ground from a descriptor, one castle of wood blocks, one character, the slingshot gesture, the live dotted arc, projectile flight, damage, block destruction, WebAudio boom.

`players[]`, `setState()` and the **`PLAYER_TURN ⇄ TURN_RESULT` loop** all exist from the first line — M1 runs one slot that cycles between those two states. This is not optional scaffolding: without the loop the input lock is never cleared (see Input safety) and the player gets exactly one shot ever, and the turn-end machinery M1 is supposed to certify never runs.

Ships `manifest.json` + `service-worker.js` so it installs on the tablet.

**Exit gate:** hand the tablet to the 4-year-old with no explanation. They fire a shot within 30 seconds and ask to do it again. Plus: the performance budget is measured, not assumed, and no projectile tunnels a block at max power.

### M2 — Turns
Slot population, HUMAN/CPU flag, turn manager, round manager, CPU solver, pass-the-device screen (human-next only), elimination, win condition, stone material, stepped platforms.
**Exit gate:** 1 human + 1 CPU, and 2 humans, both complete a match. Every player gets exactly one turn per round. Mashing the screen never fires twice, including across a pause mid-flight. Then run the P5 falsification test at 4 players on the reference iPad.

### M3 — Shell
Setup screen, HUD, scoring with reasons shown, round intro, final results with rankings and awards, Play Again / New Game / Home, parent settings panel (sound, reduced motion, learn mode, CPU difficulty), `localStorage`.
**Exit gate:** full match at 2, 3, and 4 players, then Play Again, then New Game, with no state leaking between matches.

### M4 — Delight
Bonus targets, spoken prompts, TTS, confetti, screen shake, awards, icons, launcher tile.
**Exit gate:** the §37 UX acceptance questions, answered by the kid without adult explanation.

### M5 — Poster and docs
The printable battle poster (split out of M4 because it is the only item with real platform risk — see Distribution Plan item 7), plus the documentation pass.
**Exit gate:** poster prints or saves from the installed PWA on the reference device; all four repo documents updated.

## Architecture

Single `castle-blasters/index.html`, IIFE-wrapped, organised as named sections. Logical modules inside one file, not separate files, and they must not be tangled (§31).

| Module | Responsibility |
|---|---|
| `CONFIG` | Every tunable in one block at the top. Nothing tunable lives inline. |
| `state` | The state machine. Exactly one `curState`; every transition goes through `setState()`. |
| `players` | Slot array. Creation, elimination, scoring, awards. |
| `turns` | Turn manager, round manager, turn-end detection. |
| `world` | Ground descriptor, castle descriptors, layout for 2/3/4 players. |
| `physics` | Matter.js engine, bodies, collisions, damage, culling. |
| `aim` | Gesture capture, power/angle derivation, trajectory prediction. |
| `cpu` | Shot solver, error injection, target selection, silly shot. |
| `learn` | Bonus target selection, spoken prompt, hit evaluation. |
| `audio` | WebAudio synthesis and Web Speech. |
| `render` | Canvas draw loop. Reads state, never mutates it. |
| `ui` | DOM overlays and DOM HUD. |
| `store` | `localStorage`. |

### Viewport and world

**One fixed world, no camera, no scrolling.** `WORLD_W = 1024`, `WORLD_H = 768`. All game logic works in world units. The renderer computes one uniform scale `s = min(canvas.w / WORLD_W, canvas.h / WORLD_H)`, centres the world, and letterboxes the remainder with the launcher navy `#1a2555`. The backing store is sized at `devicePixelRatio` and the context scaled once. **Every number in this document is a CSS px in world space**, never a device pixel.

**Coordinate convention: +y is DOWN, everywhere, matching Matter.** `y = 0` is the top of the world, `y = 768` the bottom. There is no second convention anywhere in this design.

**The HUD is DOM, not canvas.** It sits above the canvas in absolute CSS px and does **not** scale with the world, so it stays readable when the world is letterboxed into portrait. `DESIGN.md:23` already specifies HUD type in absolute px (20px badges, 15px pills), which only makes sense for DOM. HUD contents, exhaustively: current player pill (name + colour), that player's heart pips, round pill, that player's score pill, the bonus-target prompt pill (only when a target is active), and a **⏸ pause button** in the top corner. Nothing else.

The pause button is the only mid-match affordance, and it is load-bearing for three separate things: it is the sole entry to `PAUSED`, the sole route to the parent settings panel during a match, and the sole way to abandon a match without sitting through up to `ROUND_MAX` rounds. Tapping it opens the pause overlay: **RESUME · SETTINGS · HOME**.

### Fixed timestep

**One rate, always. `STEP_MS = 16.666 / 3 = 5.5555`.** Accumulator-driven, decoupled from `requestAnimationFrame`, three steps per 60Hz frame, capped at 8 steps per frame to avoid a death spiral after a tab stall. There is **no** conditional substepping: Matter applies gravity as a force scaled by `deltaTime²`, so a step rate that changes mid-flight changes the trajectory, and `positionIterations`/`velocityIterations` are per-`Engine.update` so towers would solve stiffer while a shot is airborne than while they settle.

Crane Stacker passes a variable `dt` (`crane-stacker/index.html:790,795`). **Do not copy that here.**

Why this rate specifically: it is the largest step at which the fastest projectile travels well under its own radius per step, which is what removes the tunnelling risk (below).

### Physics constants (all in `CONFIG`, all tuned as one set)

```
engine.gravity.y      = 1        // Matter default, stated because everything below depends on it
engine.gravity.scale  = 0.001    // Matter default
engine.enableSleeping = false    // see Sleeping, below — this is deliberate

block:      w 40, h 40, chamfer 4, density 0.004, friction 0.95,
            frictionStatic 1.2, restitution 0.05      // Crane Stacker's tuned values
projectile: radius 18, density 0.008, friction 0.4, restitution 0.2,
            frictionAir 0                              // frictionAir 0 is load-bearing, see Aiming
character:  w 36, h 44, chamfer 8, DYNAMIC, density 0.003, friction 0.9,
            frictionStatic 1.0, restitution 0.05      // must be dynamic: it has to be able to fall
```

**Speed units.** `Body.setVelocity` normalises against Matter's base delta: it sets `positionPrev = position − velocity × (body.deltaTime / 16.666)`. So a velocity handed to `setVelocity` is **world px per 16.666 ms regardless of the actual step size**. All speeds below are in those units, which makes them step-independent.

**Deriving `MAX_SPEED` instead of picking a round number.** With `gravity.y = 1`, `scale = 0.001`, flat-ground 45° range is `R = v² / (gravity.y × scale × 16.666²) = v² / 0.2778`.

- Longest shot the game can require: P1 → P4 at 4 players, castle centres at x = 128 and 896, so **768 px**.
- `v_required = √(768 × 0.2778) = 14.6`.
- **`MAX_SPEED = 18`** (≈25% headroom, `R ≈ 1166` px).
- **`MIN_SPEED = 5`** (`R ≈ 90` px, a short lob that lands just in front of you).

An earlier draft used `MAX_SPEED = 26`, which gives `R ≈ 2430` px in a 1024 px world — 2.4× the world width. That would have put the entire playable range into the first 55% of the drag and left 45% of a preschooler's gesture as undifferentiated overshoot.

**Tunnelling.** Matter.js has no continuous collision detection. Per-step displacement at `MAX_SPEED` is `18 × (5.5555 / 16.666) = 6` px, against a projectile radius of 18 and a block width of 40. Six is a third of the radius, so tunnelling is structurally impossible at these numbers rather than merely unlikely. **If `MAX_SPEED` or `STEP_MS` is ever retuned, this ratio must be rechecked.** Verifying it is part of the M1 exit gate.

**Damage.** On `collisionStart` involving the projectile, `impact = |relative normal velocity| × projectile.mass`, taking velocity from `Body.getVelocity()`. Matter's `pair.contacts[].normalImpulse` is **not** usable: it is only meaningful after the velocity solver runs and is scaled by the solver's internal delta. Projectile mass is **7.98**, not `0.008 × π × 18² = 8.14`: `Bodies.circle` builds an n-gon with `sides = ceil(min(25, radius))` forced even, so a radius-18 circle is an 18-gon of area ≈ 997. **`IMPACT_HIT = 60`** as a starting value. Working the curve backwards, `60 / 7.98 = v 7.5`, which is about **30% of full drag** — so roughly a third-power hit upward registers, and below it a block is pushed but takes no hit. At half drag (`v ≈ 10.1`) a head-on hit gives `impact ≈ 81`. Tuned at M1.

**Sleeping is off.** `enableSleeping: true` would be a bug here, not an optimisation. `Sleeping.afterCollisions` (matter.js:3958) skips any pair where either body `isStatic`, so a block asleep on the static ground can never be woken through that contact; and when a supporting block is *removed* on destruction there is no collision event at all, so the block above is never woken and `_bodiesApplyGravity` (matter.js:6547) skips sleeping bodies. The result is blocks hanging in mid-air, which destroys the one thing this product is for. It would also not help turn-end detection: Matter's `sleepThreshold` is 60 steps and the turn-end predicate fires at 20, so sleep never engages during a turn anyway. At a ~60-body ceiling Matter does not need it.

**Culling.** Remove bodies outside `x < −200 || x > WORLD_W + 200 || y > WORLD_H + 200 || y < −300`. Crane Stacker's cull (`crane-stacker/index.html:730`) is vertical-only; the horizontal bounds are added because a near-flat max-power shot can exit the world sideways.

### Art direction

**All in-game art is canvas-drawn primitives** — rectangles, circles, arcs, simple paths. No sprite sheets, no image assets, no emoji-as-art. The only images that ship are the four PWA icons from `_make_icons.py`. Four characters, distinguished by silhouette and colour, **with no mechanical differences**, auto-assigned by slot. There is no character picker in v1.

**Fonts must be loaded before the first draw.** `ctx.fillText` with a webfont that has not arrived silently falls back and does **not** re-render when it does. Every block carries a label, so this is visible on the first frames of every session. `await document.fonts.load('40px "Lilita One"')` and `await document.fonts.ready` before the first `render()`, with a plain-coloured splash until then.

### State machine (§32)

Nine states. `GAME_SETUP` folds into `PLAYER_SETUP`; `NEXT_PLAYER_READY` folds into `PASS_DEVICE`. `PLAY_AGAIN` is an **action**, not a state. Stated as a table rather than a diagram, deliberately — an earlier draft's ASCII art disagreed with its own guard list.

| From | To | Guard / trigger |
|---|---|---|
| `HOME` | `PLAYER_SETUP` | Play tapped |
| `PLAYER_SETUP` | `ROUND_INTRO` | Play tapped; requires ≥1 HUMAN slot |
| `ROUND_INTRO` | `PASS_DEVICE` | intro ends **and** the round's first living player is HUMAN |
| `ROUND_INTRO` | `PLAYER_TURN` | intro ends and that player is CPU |
| `PLAYER_TURN` | `TURN_RESULT` | turn end (settle **or** `TURN_MAX_MS`) |
| `PLAYER_TURN` | `PAUSED` | pause tapped |
| `PAUSED` | `PLAYER_TURN` | Resume tapped |
| `PAUSED` | `HOME` | Home tapped (abandons the match) |
| `TURN_RESULT` | `FINAL_RESULTS` | `alive.length ≤ 1` **or** no living HUMAN remains |
| `TURN_RESULT` | `ROUND_COMPLETE` | this was the last living player in the round order |
| `TURN_RESULT` | `PASS_DEVICE` | next living player is HUMAN |
| `TURN_RESULT` | `PLAYER_TURN` | next living player is CPU |
| `PASS_DEVICE` | `PLAYER_TURN` | "I'M READY" tapped |
| `ROUND_COMPLETE` | `FINAL_RESULTS` | `round ≥ ROUND_MAX` |
| `ROUND_COMPLETE` | `ROUND_INTRO` | otherwise |
| `FINAL_RESULTS` | `ROUND_INTRO` | Play Again (reset scores, hearts, castles; keep slots) |
| `FINAL_RESULTS` | `PLAYER_SETUP` | New Game |
| `FINAL_RESULTS` | `HOME` | Home |

Guards are evaluated **top to bottom in the order listed**; the first match wins. That ordering is what makes the end-of-match checks fire at `TURN_RESULT` rather than waiting for `ROUND_COMPLETE`. It matters: if the only human is knocked out on the first turn of a round in a 1-human/3-CPU match, an end-of-round check would let three bots take their turns first, which is exactly the empty-room case the guard exists to prevent.

`PAUSED` is enterable from `PLAYER_TURN` only, via the HUD ⏸ button.

**`ROUND_INTRO` branches on the same human/CPU test as `TURN_RESULT`,** and it has to. Round rollover leaves `TURN_RESULT` via `ROUND_COMPLETE`, bypassing the pass-device guard entirely; without the branch above, a 2-human match would end round N on Player 2's turn and open round N+1 on Player 1's turn while Player 2 is still holding the tablet. That is the Round-1 missing-`PASS_DEVICE`-edge bug reappearing one level up.

### Player slot

```js
{ id: 1, name: 'PLAYER 1', kind: 'human' | 'cpu',
  characterId: 'nim', color: '#2eb8ff', castleId: 0,
  hearts: 3, alive: true, score: 0,
  stats: { blocksFelled: 0, bestShotDamage: 0, targetsHit: 0,
           directHits: 0, selfHits: 0 } }
```

CPU difficulty is a **single match-wide setting** (`cpuLevel: 'easy' | 'medium' | 'hard'`, default `easy`, set in parent settings, persisted), not a per-slot field. A per-slot field with no UI to set it would leave the silly shot — one of the three things this product is for — permanently unreachable.

`castleId` is separate from `id` because it is needed as a castle index regardless, and because v2 teams need several players to share one castle.

### World descriptors

```js
// ground: static platforms, world coords, +y DOWN
// x, y are the LEFT and TOP edges. Bodies.rectangle takes a centre, so the
// conversion is: Bodies.rectangle(x + w/2, y + h/2, w, h, { isStatic: true })
[ { x: 0,   y: 700, w: 1024, h: 68 },   // base ground, top surface at y = 700
  { x: 300, y: 620, w: 180,  h: 20 } ]  // stepped platform, top surface at y = 620
```

```js
// castle: block descriptors. gx = column (0 = leftmost), gy = row (0 = bottom).
// Conversion, stated so there is no ambiguity given +y is down:
//   worldX = castleBaseX + (gx + 0.5) * BLOCK_W
//   worldY = platformTopY - (gy + 0.5) * BLOCK_H
[ { gx: 0, gy: 0, mat: 'wood',  label: 'B' },
  { gx: 1, gy: 0, mat: 'stone', label: '7' }, ... ]
```

Keeping ground and castle as plain descriptors is what lets M1's power-curve tuning survive the introduction of stepped platforms at M2, and what makes a future builder phase additive rather than a rewrite.

### Layout and block budget

Block 40 × 40. Castle footprint 3 columns (120 px).

| Players | Slice | Castle centres | Gap | Blocks | Rows |
|---|---|---|---|---|---|
| 2 | 512 | 256, 768 | ample | 12 | 4 |
| 3 | 341 | 171, 512, 853 | 221 | 9 | 3 |
| 4 | 256 | 128, 384, 640, 896 | 136 | 9 | 3 |

**This table exists because the core thrill is "a stack comes apart," and a 5-block pile does not come apart, it tips.** Nine blocks in three rows is the floor at which destruction reads as destruction. If M2 playtesting shows 4-player castles feel thin, the fix is to make **2 players the default with a 4-row castle**, not to shrink further.

Castles sit on stepped platforms at alternating heights so a far castle is not fully occluded. Heights are tuned at M2.

### Aiming (P2)

- **Activation region:** touch down anywhere inside the active player's slice (widths above), at any height. Not a radius around the character — §7 demands forgiving input and a 4-year-old will not reliably hit a small hotspot.
- **Drag vector:** `drag = clamp(pointerStart − pointerNow, MAX_DRAG)`, `MAX_DRAG = 220`. **Pull back to fire forward**, slingshot semantics: dragging left and down launches right and up. `dir = normalize(drag)`.
- **Power curve:** `speed = MIN_SPEED + (|drag| / MAX_DRAG) ^ 1.35 × (MAX_SPEED − MIN_SPEED)`, i.e. 5 → 18. The exponent gives fine control at low power. Tuned at M1.
- **Firing:** `Body.setVelocity(projectile, { x: dir.x * speed, y: dir.y * speed })`. The slingshot band is **drawn**, never simulated with a `Constraint`.
- **Trajectory preview:** computed by **iterating the exact same integrator the engine uses**, for up to **420 steps**, plotting every 8th point as a dot. 420 is not arbitrary: at `STEP_MS = 5.5555` the longest required shot (768 px at `v ≈ 14.6`) takes **222 steps**, a flat-out max-power 45° shot takes **274**, and a near-vertical lob at `MAX_SPEED` takes about **389**. A 200-step cap — which an earlier draft carried over from a one-step-per-frame design — would have stopped the 4-player arc roughly 80 px short of the enemy castle while it was still descending, on exactly the shot `MAX_SPEED` was derived from. Do **not** use a closed-form parabola. Matter's `Body.update` (matter.js:2332-2338) updates velocity and *then* advances position by the new velocity, so the true closed form is `p(n) = p₀ + u·n + a·n(n+1)/2`, not `p₀ + u·n + ½·a·n²`. The `½·a·n` difference is linear in n: at `STEP_MS = 5.5555` it is about **3.4 px** on the longest required shot and about **6 px** on a near-vertical lob. Small, but it grows with flight time and it is free to avoid — iterating is a few hundred adds per frame and is exact by construction, where a closed form has to be re-derived every time the step rate changes. This is also why the projectile has `frictionAir: 0`: any non-zero value makes the path non-parabolic *and* step-rate-dependent.
- **Truncation:** the arc stops at the first ground or block intersection, at the **cull bounds** (`x < −200 || x > WORLD_W + 200 || y > WORLD_H + 200`), or at 420 steps, whichever comes first. Note the cull bounds and not `y = 0` on the top edge: a near-vertical shot legitimately climbs above the world to about `y = −43` and comes back, and truncating at the top of the screen would draw a lie.
- **Minimum drag:** `MIN_DRAG = 28`. Releasing below it **cancels the shot** rather than firing it. Without this, the activation region is a 256 × 768 px slab in which any stray tap fires a live 90 px lob and burns the turn — for a player the rest of this document is explicitly designing around double-taps and imprecise touch (§7).
- **Spawn:** the projectile spawns 30 px above the character's top edge, and collides with nothing for its first 3 steps, so a low-power shot cannot detonate on the shooter's own castle at the moment of launch.

### Turn end (this is what prevents soft locks)

The turn timer is deferred, so this is the **only** thing that ends a turn. Two conditions, whichever fires first:

1. **Settled.** Every dynamic body satisfies `|velocity| < 0.2 && |angularVelocity| < 0.02` for 20 consecutive fixed steps (≈111 ms).
2. **Hard cap.** `TURN_MAX_STEPS = 2160` accumulated fixed steps from the moment of firing (12 s of simulated time at `STEP_MS`). Matter bodies can jitter below any reasonable threshold indefinitely. On expiry, zero all velocities, then transition.

   **Counted in simulation steps, not wall clock, and deliberately so.** A `performance.now()` deadline would expire while the game sits in `PAUSED`, and the state table has no `PAUSED → TURN_RESULT` edge — so the transition would either be dropped (the turn never ends after resume) or fire out of `PAUSED` and break the single-owner `inputLocked` discipline. Steps do not advance while paused, so the problem cannot arise.

Either path transitions `PLAYER_TURN → TURN_RESULT`. There is no third path.

This predicate is **inspired by, not identical to**, Crane Stacker's. `crane-stacker/index.html:741-745` tracks `restFrames > 20` per block since landing, in a `WeakMap`, under a variable `dt`, to count landings. This one is a global check over all dynamic bodies on a fixed step. Same thresholds, different scope; write it fresh rather than copying the function.

### Health and elimination

**Hearts are the only health model, and only the character carries them.** Each player starts with `hearts: 3`, drawn as three countable pips, never a bar (§28).

- Character struck by a projectile above `IMPACT_HIT` → **−1 heart**, capped at one heart per incoming shot.
- **Character falls.** Checked once at turn end: if the character's centre has ended up more than **120 px below its own platform's top surface**, or outside its own castle's horizontal slice, it fell → **−1 heart**, and it is then repositioned standing on whatever remains of its castle (or on the bare platform if the castle is gone). At most one fall-heart per turn, and it does not stack with the projectile-hit heart in the same turn.
- Character culled off-screen (past the world bounds entirely) → **immediate elimination**, regardless of hearts.
- `hearts === 0` → eliminated.

The fall rule is what makes the slogan literally true. Without it, knocking an enemy character off its collapsing castle onto the ground at `y ≈ 700` costs nothing at all, because the cull bound is `y > 968` — falling would only matter off the left and right edges, which almost never happens. The character body is dynamic (see Physics constants) specifically so it can be toppled.

**The castle is cover and points, not health.** Destroying it exposes the character and scores, but it never directly costs a heart. This is deliberate: an earlier draft also drained hearts from a castle block-count floor, which produced three different readings of when and how often it fired and, under one of them, killed a flattened player inside a single round no matter what they did. One rule a 4-year-old can state out loud — *you lose when your guy falls* — is worth more than a richer model nobody can predict.

Eliminated characters leave with a puff and a wobble, never an injury animation (§13).

"Last player standing" means `alive.length ≤ 1`.

### Scoring and awards

Points, shown with the reason as a floating label (§23):

| Event | Points | Label |
|---|---|---|
| Block damaged, not destroyed | 10 | `+10 HIT!` |
| Wood block destroyed | 25 | `+25 SMASH!` |
| Stone block destroyed | 50 | `+50 STONE!` |
| Direct character hit | 100 | `+100 DIRECT HIT!` |
| Bonus target hit | 150 | `+150 GREAT FIND!` |
| Opponent eliminated | 200 | `+200 KNOCKOUT!` |
| Hitting your **own** castle or character | 0 | `OOPS!` — never negative (§2.3) |

Bonus targets only ever appear on an **opponent's** castle, so `+150 GREAT FIND!` and `OOPS!` can never contend for the same collision.

**Awards.** Assigned greedily in this order; each has a `> 0` precondition, and any player left without one gets 🎈 **GOOD GAME**. Ties break to the lower player id.

| Order | Award | Source | Precondition |
|---|---|---|---|
| 1 | 🏆 CHAMPION | the match **winner** | always (exactly one) |
| 2 | 💥 BIGGEST BOOM | highest `bestShotDamage` | `> 0` |
| 3 | 🧱 WALL BREAKER | most `blocksFelled` | `> 0` |
| 4 | ⭐ LEARNING STAR | most `targetsHit` | `> 0` |
| 5 | 🎯 GREAT AIM | most `directHits` | `> 0` |
| 6 | 😄 SILLY SHOT | most `selfHits` | `> 0` |
| — | 🎈 GOOD GAME | fallback | anyone still unawarded |

**CHAMPION is the winner, not the high scorer.** The win condition is last-player-standing with points as the tiebreak, so a score-based CHAMPION could print "PLAYER 3 WINS" beside "🏆 CHAMPION: PLAYER 1" on the same screen, in front of a 4-year-old. The preconditions matter for the same reason: with `learnMode: 'off'` every player has `targetsHit: 0`, and an award for hitting zero targets in a mode where targets do not exist is worse than no award.

### CPU

**Target selection:** among living opponents, the one whose castle has the **fewest** standing blocks; ties to nearest. Then aim at the **lowest standing block** of that castle — toppling from the base is both more effective and more spectacular. Targeting the weakest is also what makes matches end; targeting the healthiest opponent would mean the CPU never finishes anyone off and, at 4 players with ±12° error, a match could run past twenty rounds.

**"Standing"**, used here and in scoring, means: the block body is still present in the world (not culled or destroyed) **and** its centre is still within its own castle's horizontal slice. A block knocked into a neighbouring slice is debris, not cover.

**Solution:** solve the ballistic angle for the target at a chosen speed. `MAX_SPEED` reaches 1166 px against a longest required shot of 768 px, so a solution always exists on open ground; the failure case is an intervening castle. Fallback chain: (a) retarget to the nearest living opponent, (b) if still blocked, fire at max power at 45° toward the target. Never a skipped turn.

**Error injection:** angle error sampled uniformly from ±12° (easy), ±6° (medium), ±2° (hard); power jitter ±8% / ±4% / ±1%.

**Silly shot.** On easy only, **12% of shots** are replaced by a deliberate near-vertical launch (75–88°, low-to-mid power) that lands on or near the bot's own castle. Angular error alone lands short or long on the correct side and essentially never behind the shooter, so this is the only mechanism that produces the self-demolition described in What Makes This Cool.

**Presentation:** a 700 ms "thinking" pause, then a visible aim animation using the same dotted arc a human sees, then fire. The kid gets to watch the bot line up and miss.

### Learning (`learn`)

- **Label generation.** Every castle is built with a fixed mix: **5 letters and 4 numbers** in the 9-block layouts, **7 and 5** in the 12-block layout, positions shuffled per match. Letters are drawn from A–Z, digits from 0–9, without repeats inside one castle. This mix is not cosmetic — it guarantees that both `letters` and `numbers` mode always find an eligible block on every castle, which a purely random labelling does not.
- **Cadence:** at most one bonus target per turn, on 50% of turns, only when `learnMode ≠ 'off'`. The target castle is chosen uniformly from **living opponents** (never the active player's own), then the block uniformly from that castle's standing blocks whose label matches the mode. Cleared at turn end whether hit or not.
- **Prompt:** the block glows with a `#ffd700` ring, the HUD prompt pill shows `HIT 7`, and TTS speaks "hit the seven." Visual and audio both, never audio alone (§27).
- **On miss:** nothing. No sound, no message, no penalty (§2.3).
- **`learnMode: 'off'` means:** blocks **keep their labels** (the labels are the art, and removing them would change every castle), nothing is spoken, and no bonus targets ever spawn. Off removes the prompts, not the alphabet.

### Input safety (§33)

**One flag: `inputLocked`, owned by the state machine.** Every pointer handler returns early when it is set. There is no second in-flight guard; all fire paths route through a single `fireShot()` that is a no-op unless `curState === PLAYER_TURN && !inputLocked`.

- Set on: shot release, and on entering `TURN_RESULT`, `PASS_DEVICE`, `ROUND_COMPLETE`, `FINAL_RESULTS`, `PAUSED`, or any visible overlay.
- Cleared on: entering `PLAYER_TURN` **only when no projectile is in flight**.

That last clause is load-bearing. Pausing mid-flight and resuming re-enters `PLAYER_TURN`; without it the lock would clear while the shot was still travelling and the player could fire twice in one turn.

Overlay buttons ("I'M READY", "PLAY AGAIN") get a 400 ms debounce plus immediate self-disable on first activation, because a 4-year-old double-taps everything.

### Audio (P8)

Copy from Crane Stacker, and note that the important parts are not the obvious ones:

- `initVoices()`, `LETTER_NAMES`, `SPEAK_RATE`, `SPEAK_PITCH` — the visible pattern.
- **`speechSynthesis.resume()` before every `speak()`** (`crane-stacker/index.html:328`). Without it Chrome silently stalls. This fix took two versions to find (`crane-stacker/CLAUDE.md:110`).
- **The `rate = 10`, `volume = 0` unlock utterance on the first user gesture** (`crane-stacker/index.html:300-310`). Without it iOS never speaks.
- **`AudioContext` needs the same treatment:** create it lazily and call `ctx.resume()` inside the first user-gesture handler, or WebAudio is silent on iOS.

Synthesized cues, no files: **boom** (white-noise burst through a lowpass sweeping 1200→80 Hz, 400 ms), **launch** (rising sine sweep, 120 ms), **thunk** (short filtered click), **ding** (decaying 880 Hz sine).

### Reduced motion

`reduceMotion` (persisted; defaults to `window.matchMedia('(prefers-reduced-motion: reduce)').matches`) disables **screen shake and confetti only**. It does not disable trajectory dots, block motion, or anything else carrying game information — those are the game.

### Persistence

`localStorage`, single key `castleBlasters.v1`. Exactly four things: `learnMode` (`off`/`letters`/`numbers`), `soundOn`, `reduceMotion`, `cpuLevel`.

Deliberately **not** persisted: match state, scores, player counts, slot configurations, high scores. A "high score" is meaningless in a local free-for-all, and a half-restored match is more confusing than a fresh one. A refresh mid-match returns to `HOME`. This mirrors the reasoning already recorded in `printables/CLAUDE.md` about not restoring a half-built sheet.

### Performance budget (measured at M1, not assumed)

- Dynamic bodies at 4 players: 4 castles × 9 blocks = 36, plus 4 characters, plus 1 projectile, plus debris. Working ceiling **~60 awake bodies**.
- Sleeping is off (see Physics constants), so all of them are always simulated. At 60 bodies this is well inside Matter's comfortable range.
- **M1 gate:** instrument a frame-time counter, drop 40 blocks, fire a shot at max power, record the actual number on the real tablet, and confirm no tunnelling. Whatever the number is, it goes into `castle-blasters/CLAUDE.md`. If it does not hold, reduce castle rows before reducing player count.

## Distribution Plan

Existing pipeline covers this. No new infrastructure.

1. `castle-blasters/` containing `index.html`, `manifest.json`, `service-worker.js`, `icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `favicon-32.png`, `_make_icons.py`, `README.md`, `CLAUDE.md`.
2. **`manifest.json` uses `"display": "standalone"`.** The other two apps differ (`crane-stacker` is `fullscreen`, `printables` is `standalone`); standalone is chosen here because M5 needs a print path and printing from a fullscreen installed PWA is less reliable.
3. **`"orientation": "landscape"`** is set, but do not rely on it: iOS/WebKit implements neither the manifest `orientation` member nor `screen.orientation.lock()`, so on the reference device it is inert. It is correct and free on Android Chrome. What actually upholds P5's geometry on iPad is the letterboxed world plus the DOM HUD, which is why portrait is a tested case rather than "best-effort."
4. **M1–M4 ship to `main` at the real path** `/castle-blasters/`, with **no launcher tile** (the tile lands in M4's final step). Not to Vercel preview URLs: every push mints a new preview origin, so each gets its own service worker registration, Cache Storage and `localStorage`, meaning the kid's installed app must be deleted and reinstalled on every iteration and loses its settings each time. Preview deployments can also sit behind Vercel Deployment Protection, which would block an unauthenticated iPad outright. Shipping unlinked to the real origin costs one line of scope and avoids all of it.
5. Launcher tile added to `index.html` inside `<main id="apps">` at M4, pointing at `./castle-blasters/` with `./castle-blasters/icon-512.png`. Icon uses slot-2 golden yellow `#ffd700`. **The same commit must bump `CACHE_VERSION` in the ROOT `/service-worker.js`** (currently `kid-apps-launcher-v2.1`). That service worker is cache-first and precaches `./index.html`, so without the bump every installed launcher keeps serving the cached tile-less page forever and the new tile never appears on the kid's tablet — the exact failure the Constraints section warns about, applied to the one service worker it is easy to forget.
6. Service worker scoped to `/castle-blasters/`, precaching the app shell plus the Matter.js and Google Fonts URLs. `CACHE_VERSION = 'castle-blasters-v1.0'`, bumped on every deploy without exception.
7. **The poster needs a fallback specified now, not discovered at M5.** `window.print()` from an installed iOS home-screen web app has a long history of silently doing nothing. `printables/` is not evidence to the contrary: its own `CLAUDE.md` states under Known gaps that *"the print path has only been checked through the browser's print preview"* and has never been printed from an installed PWA. So M5 ships **print or save**: attempt `window.print()` on a print view, and always also offer the `canvas.toDataURL()` image in an `<img>` the parent can long-press to save, plus `navigator.share({ files: [...] })` where available.
8. `vercel.json` already sets `Cache-Control: no-cache` on `/(.*)/service-worker.js` and `Service-Worker-Allowed: /`. No change needed.
9. Verify a deploy with `curl -s https://apps.bryllelagunda.com/castle-blasters/service-worker.js | grep CACHE_VERSION` — the constant lives in the service worker, not in `index.html`.

- Conditional substepping (3 substeps only while a shot was in flight) would have produced three different arcs in one game, since Matter scales gravity by `deltaTime²`. Now one fixed rate always.
- `MAX_SPEED = 26` gave a 2,430 px range in a 1,024 px world. Now derived from the longest required shot: 18.
- `enableSleeping: true` would leave blocks hanging in mid-air, because `Sleeping.afterCollisions` (matter.js:3958) skips pairs containing a static body and a removed support generates no collision event at all. Sleeping is now off.
- CPU targeted the *healthiest* opponent, so matches never ended. Now targets the weakest, with `ROUND_MAX` as a backstop.
- `cpuLevel` was a per-slot field with no UI, leaving the easy-only silly shot unreachable. Now one match-wide persisted setting.
- CHAMPION was awarded on score while the winner was last-standing, so the two could name different players on the same screen.
- Two contradictory y-axis conventions in adjacent code blocks.
- A castle-block-count heart drain admitted three different readings; removed entirely in favour of "you lose when your guy falls."

**Round 3 — gaps between the design's stated thesis and its rules:**
- "You lose when your guy falls" was the justification for simplifying the health model, but no rule made falling cost anything; the cull bound is 268 px below the ground, so a toppled character just sat there. Added as an explicit turn-end check.
- The trajectory preview cap (200 steps) was a leftover from the pre-substepping draft and stopped the 4-player arc ~80 px short of its target while still descending. Now 420, derived from the actual flight times.
- Round rollover bypassed `PASS_DEVICE` entirely, so a 2-human match opened each new round with the wrong person holding the tablet.
- `PAUSED`, Home and the parent settings panel were all in the design with no button anywhere in the exhaustively-specified HUD.
- `TURN_MAX_MS` was wall-clock, which would have expired during a pause into a state transition the table forbids.
- Adding the launcher tile needs a bump to the **root** service worker, which no part of the plan mentioned.
